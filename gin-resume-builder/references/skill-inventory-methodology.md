# 技能盘点方法论

> 适用：用户说「我会什么」「盘点技能」「挖掘能力」「整理职业优势」，或希望从经历中找出可用于求职的技能时使用。
>
> 本文优化现有技能清单维护与技能深挖流程，不新建另一套职业知识库。事实仍以 `原始事实/` 为真源，技能只有在用户确认后才写入 `skills.md`。

## 一、技能盘点要解决什么

招聘方关心的是：候选人能否在目标岗位的场景和约束下，稳定解决某类问题。因此，技能盘点要把零散经历转换为可验证、可命名、能指向结果的技能候选，同时保留证据、个人贡献和适用边界。

一次盘点可以有不同目标，先确认当前目标再开始提问：

- 全面盘点已有技能；
- 从某段工作或项目经历中发现技能；
- 补充某项技能的证据和方法；
- 针对目标 JD 查找匹配技能；
- 区分技能、经验、能力和资源线索。

### 目标卡

```text
本次目标：
目标岗位或使用场景：
希望形成的产物：技能清单 / 技能详情 / 证据 / JD 匹配
已有信息：
会改变判断的最大缺口：
```

如果已有信息足以决定下一步，就直接开始盘点；只追问会改变技能候选、证据强度、写入位置或 JD 匹配结果的信息。

## 二、四类候选对象

盘点过程可以发现四类对象，但它们的落盘位置不同，不能全部写成技能：

| 对象 | 判断问题 | 主要落点 |
|---|---|---|
| 能力 | 能否在不确定环境中持续解决一类问题？ | 通用能力或技能详情 |
| 技能 | 是否有可命名、可操作、可复用的方法或工具？ | `skills.md` |
| 经验 | 在什么时间、场景、规模和约束下实际处理过什么？ | `work_history.md` / `projects.md` |
| 资源线索 | 能在授权和合规边界内触达、调动什么要素？ | 附着到已有事实、证据或岗位匹配信息 |

「我沟通好」「我有资源」「我经验丰富」只是待拆解的线索。未经行为、结果或可核验材料支持，不直接写入技能清单。

## 三、盘点对话流程

### Step 1：锁定对象和目标

先选定一段经历、一项工作动作或一个目标岗位。不要把整段职业生涯混成一个问题。

### Step 2：概念拆解

把用户的概括拆成对象、场景、动作、结果、证据和边界。遇到「能力」「资源」「负责」「擅长」等词，优先问它在当前经历里具体指什么。

### Step 3：动作还原

用动宾结构还原用户做过的动作：对象是谁、做了什么、规模多大、持续多久、使用了什么工具或方法。

### Step 4：决策和结果

追问第一步行动、关键判断、备选方案、选择理由，以及前后变化、产出、规模和验证者。数字不清楚时记录缺口，不替用户补数字。

### Step 5：提炼技能

由 Agent 提出候选名称和可复用方法，让用户修改或确认。能复用于相邻场景才提炼为技能；只能证明发生过一次时保留为经历或证据。

### Step 6：验证和写入

核对证据、个人贡献、可迁移范围、适用边界和目标岗位相关性。先整批展示候选技能及其佐证，用户确认后才调用 `append-skill`；详情和 STAR 证据继续按现有流程写入。

全程一次只问一个问题。优先选择能最大幅度改变判断的问题，避免把盘点变成固定问卷。

## 四、证据与可迁移性

证据可以来自经历事实、作品、数据、证书、使用记录、第三方反馈或多个场景的一致行为。证据强度必须与主张匹配。证书只能证明学习或通过考试，不能单独支持技能确认：

- 只有愿望或自我评价：不入库；
- 有个人记录或一段具体经历：可作为候选；
- 有作品、数据、使用记录或具体第三方反馈：支持确认；
- 有独立第三方确认、长期结果或多个场景复现：支持较高熟练度或通用能力。

「可迁移」不是「全球通用」的硬门槛。分别记录：

- 可迁移的方法：换客户、团队或相邻行业仍可使用的判断和操作；
- 场景专属优势：依赖某行业、平台、区域、关系或权限，但对目标岗位仍有价值；
- 不适用边界：换环境后需要补充的知识、资源或权限。

能教会别人写成 SOP 是增强证据；无法完整写成 SOP 时，也可以用多场景复现、作品、结果和第三方反馈证明能力。

## 五、资源线索的专门追问

资源不等于技能，也不自动等于求职优势。出现资源线索时，至少核对：

1. 资源类型：客户、渠道、供应商、合作伙伴、人才、信息源、社群或其他；
2. 触达关系：认识、可联系、愿意合作，还是已经承诺；
3. 激活记录：过去实际调动过什么，产生了什么结果；
4. 时效与迁移：换公司后是否仍然有效；
5. 权限与合规：是否涉及原公司机密、个人隐私、竞业或授权限制。

资源只能在事实和用户确认的边界内用于 JD 匹配、求职信或面试准备，不在技能清单中伪装成技能，也不承诺用户无法控制的外部结果。

## 六、产物与知识库回流

| 产物 | 写入位置 | 规则 |
|---|---|---|
| 已确认技能 | `原始事实/skills.md` | 用户确认后逐条写入 |
| 技能方法和四维详情 | `原始事实/skill_details.md` | 先确认，重建 `facts.yaml`；反事实及边界沿用行为证据的 `Boundary` 段或 claim 的 `boundary` / `risk_notes` |
| STAR 行为证据 | `原始事实/behavioral_evidence/` | 先 stage，再经用户 OK 确认 |
| 工作或项目事实 | `原始事实/work_history.md` / `projects.md` | 追加不覆盖 |
| 待验证项 | 对话状态、claim 风险或 JD gap | 验证后回流，不当作已确认技能 |

回流时使用现有字段，不虚构新的存档格式：技能条目通过事实佐证溯源：专属能力的「佐证」或通用能力的「场景」保留来源 `fact_id`；行为证据沿用 source/confidence 字段，并在已有 `Boundary` 段记录适用边界；用户确认状态由现有的 stage/confirm 写入门禁体现。资源线索不单独建技能条目，确认后附着到已有工作或项目事实、行为证据、claim 风险或目标岗位备注；没有对应 `fact_id` 的资源只留在当前对话的待验证项，不能进入技能清单、JD 匹配或求职材料。简历与求职材料只能使用已确认技能和已回流事实。

### 盘点结束快照

每轮盘点结束时输出一份对话快照，不新建第二套知识库：

```text
已确认技能：
已形成证据模式：
仍待验证的技能或资源线索：
与目标岗位的主要匹配点：
下一步最值得补的一个证据：
```

已确认技能回读现有知识库；待验证项留在当前对话、claim 风险或 JD gap，验证后再回流原始事实。

## 七、职业表达转换

同一份盘点结果可以按用途转换：

- 简历：技能名 + 熟练度/证据 + 结果；
- 面试：情境—行动—结果—关键判断—边界；
- 求职信：一个岗位匹配点 + 一个真实证据；
- JD 匹配：要求—直接证据—相邻证据—缺口—补证动作。

转换时只改变表达，不增加知识库中没有的事实。

## 八、方法来源与适配

- [dbs-goal](https://github.com/dontbesilent2025/dbskill)：转化为目标卡与一次一个高信息增量问题。
- [dbs-deconstruct](https://github.com/dontbesilent2025/dbskill)：转化为能力、技能、经验、资源线索的概念拆解。
- [dbs-decision](https://github.com/dontbesilent2025/dbskill)：转化为事实、证据模式、盘点结束快照与待验证问题，复用现有知识库。
- 用户提供的《什么是技能》：吸收动作化描述、具体情境和可迁移方法的识别思路；不把“全球通用”或“必须写成 SOP”设为技能成立的硬门槛。
