# 技能清单标准（skills.md 维护规范）

> 涉及技能录入、技能清单维护、简历「技能」板块组装时必读。
> 数据文件：知识库 `原始事实/skills.md`；本文是唯一定义来源。
> 技能清单分两段：**通用能力** 与 **专属能力**。

## 一、什么算「技能」（定义与两类结构）

**技能 = 可验证、可迁移、可被行业通用词命名的能力单元。** 三个条件同时满足才收：

1. **可验证**——面试能被考核，或拿得出佐证（经历事实 / 作品 / 证书）
2. **可命名**——招聘平台上有通用叫法，HR 和 ATS 搜得到
3. **可指向产出**——说得清「用它做成过什么」

### 两类技能

| | 专属能力（Domain Skills） | 通用能力（Transferable Skills） |
|---|---|---|
| 定义 | 绑定具体产出，有明确验证标准 | 不依附行业岗位，可迁移到不同场景 |
| 验证方式 | **可观察的输出**：产出存在，能力就存在 | **多情境行为一致性**：单一结果不构成证明，须 3+ 不同场景的行为模式 |
| 例子 | 商务谈判、渠道管理、SQL、英语 | 沟通、协作、批判性思维、适应性、情绪智力、项目管理、数字敏度 |

- 专属能力四类：业务能力（商务谈判、招投标、渠道管理）、管理与方法（团队搭建、经营计划拆解、SOP 标准化）、工具与技术（CRM、Excel/BI、SQL）、语言（英语-商务沟通；语言同时是能力放大器，价值高于普通专属能力）
- 通用能力参考清单：沟通 / 批判性思维（问题解决）/ 适应性 / 情绪智力 / 协作 / 项目管理 / 数字敏度——不限于此，但必须可验证

### 明确不收（边界）

| 看起来像，但不是技能 | 例子 | 归属 |
|---|---|---|
| 无证据的素质宣称 | 「我沟通好」「抗压能力强」「责任心强」 | 信念，不是能力；除非按通用能力证据标准补足 3+ 场景 |
| 经历成果 | 带过 15 人团队、做过 1.35 亿营收 | 工作/项目事实（是佐证，不是技能） |
| 岗位头衔 | 销售总监 | 职位 |
| 证书 | PMP、CPA、CET-6 | 证书板块（证明学过，不证明表现；可作佐证） |
| 无区分度项 | 精通 Office、会用微信 | 直接拒收 |

常见误区：「做成过 = 会做」（一次成功可能是风口或运气，能力需要可复现）；「别人说我强 = 我强」（需多个独立来源指向同一结论）。

## 二、命名格式

1. **2-8 个汉字**（工具名除外），名词或动名词，能独立成词
2. **用行业通用名**，与 BOSS/猎聘等平台关键词对齐，不自造：✅ 渠道管理 ❌ 渠道的事儿都懂
3. **名字里不带修饰**——不带熟练度、不带年限、不带程度词：✅ 商务谈判 ❌ 很强的商务谈判能力、5 年商务谈判（熟练度/证据强度是独立字段，不写进名字）
4. **工具用官方写法**：Excel、SQL、Salesforce；组合用 `/`：Excel/BI
5. **同名归一**：一个技能全库只保留一种写法，不混用「CRM」与「客户关系管理系统」
6. **颗粒度 = 能被单独考核的最小单元**：「销售」太宽要拆（商务谈判 / 大客户经营 / 渠道管理）；「Office 三件套」太粗，要写就写具体的（Excel 数据透视）
7. 通用能力用标准能力名（沟通 / 协作 / 适应性……），不自造组合词

## 三、条目书写格式

skills.md 用两个 `## ` 分节，条目各归其段：

```
## 通用能力
- 能力名（证据：强/中）｜场景：fact_id-一句话行为；fact_id-一句话行为；fact_id-一句话行为

## 专属能力
- 技能名（熟练度）｜佐证：来源 fact_id 或一句话可验证场景
```

### 专属能力条目

- **熟练度三档**（不许夸大，面试必验证）：
  - **熟练**：能独立负责复杂场景，且能带人/定标准
  - **掌握**：能独立使用完成工作，不需指导
  - **了解**：知道原理、实操少
  - 语言类用场景词代替档位：英语（商务沟通）/ 英语（读写流利）
- **佐证必填**：指向知识库 fact_id（如 W1、P2），或一句可验证场景；拿不出佐证的技能不得确认写入

### 通用能力条目

- **证据强度两级入库**（弱/不可信不入库）：
  - **强**：3+ 个不同场景的完整 STAR，行为模式清晰
  - **中**：1-2 个完整 STAR，有证据但不足以确立模式
  - 弱（自己宣称但讲不清细节）/ 不可信（只有主观结论）→ 拒收或回炉深挖
- **场景必填**：列出支撑场景的 fact_id + 一句话行为描述，2 个起
- 多来源交叉验证（自己说 + 同事/客户/下属独立反馈一致）为可选增强，有则在场景后注明「三方一致」

### 示例

```
## 通用能力
- 沟通（证据：强）｜场景：W1-向经销商拆解压库政策并达成续约；W2-跨部门争取促销预算获批；P1-主持 6 场经销商培训答疑
- 适应性（证据：中）｜场景：W1-接手下滑大区后三个月内重构打法；W2-从 KA 卖场转经销渠道快速上手

## 专属能力
- 商务谈判（熟练）｜佐证：W1-主导 2 家省级经销商签约，单笔 3000 万
- SQL 取数（了解）｜佐证：自学完《SQL 必知必会》，工作中独立出过周报取数
- 英语（商务沟通）｜佐证：W2-独立接待海外客户验厂 3 次
```

旧格式（无 `## ` 分节）自动视为专属能力段，facts_parser 向后兼容。

## 四、确认门禁（写入流程）

**所有技能（两类同规）必须先发给用户确认，确认后才允许写入 skills.md。无例外。**

| 入口 | 流程 |
|---|---|
| 用户自报（访谈 / 更新知识库） | 整理成清单（专属：技能名+熟练度+佐证；通用：能力名+证据强度+场景）→ 整批展示 → 用户确认的条目才逐条 `append-skill` 写入 |
| AI 推断（做简历 / JD 分析时从经历发现新技能或通用能力） | 列出「建议新增」+ 推断依据（来自哪段经历/fact_id）→ 用户确认 → 写入后才允许上简历 |

配套硬规则：

- 简历「技能」板块、求职材料中出现的技能，**必须已在 skills.md 中**；AI 推断但未经确认的不得使用
- 确认时给用户看的必须包含佐证/场景，用户确认的是整条
- 用户未确认的条目不暂存、不落盘，直接丢弃（下次需要时重新提）

## 五、技能深挖与通用能力发现

- **专属能力详情**：按 `references/skill-mining-playbook.md` 支架式深挖（选择题化 / 填空拆解 / 示例锚定 / 草稿纠偏，漏斗顺序，STAR-Plus 五维 + 反事实验证）；核心技能挖全五维，其余维持一行佐证
- **通用能力发现**：用 playbook 的「通用能力发现模式」——从具体经历还原行为，追问 3+ 个不同场景的 STAR，按证据强度评级；严禁直接问「你沟通能力怎么样」
- **STAR 行为证据补充**：在 KB 访谈主线中，当用户说出具体工作/项目/技能/优势场景时，可同步按 `references/tacit-mining-methodology.md` 生成 `behavioral_evidence/` 碎片。对应技能需要详细描述时，可用 `scripts/mining/evidence_to_skill_detail.py --skill 技能名` 转成 `skill_details.md` 五维块草稿
- 写入 `skills.md` 前，应运行 `scripts/mining/skill_validator.py --skill 技能名` 校验证据数量与已声明档位是否匹配；证据不足时不得写入更高档位
- 深挖产物经用户确认后写入 `原始事实/skill_details.md`（技能五维详情）或 `原始事实/behavioral_evidence/`（STAR 碎片），运行 `facts_parser.py` 重建；facts.yaml 的 `skill_details` 与 `behavioral_evidence` 字段供简历与面试素材取用

## 六、清单维护命令

```bash
# 查看全部已确认技能（按两段分组显示）
python3 kb_interview.py list-skills [--kb 路径]

# 写入专属能力（仅限用户已确认的条目，逐条）
python3 kb_interview.py append-skill --text '商务谈判（熟练）｜佐证：W1-……' [--kb 路径]

# 写入通用能力
python3 kb_interview.py append-skill --type general --text '沟通（证据：强）｜场景：W1-……；W2-……；P1-……' [--kb 路径]

# 删除：手动编辑 skills.md 删掉对应行，然后重建派生数据（含审计链）
python3 facts_parser.py [--kb 路径]
```
