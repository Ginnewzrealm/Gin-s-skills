# 非技术业务访谈协议

## 首问

优先从真实案例开始：

> 我们先不讲标准流程。就拿最近一次真实发生的业务来说，你最开始是怎么知道这件事需要你处理的？

如果用户已经给出起点，直接追问下一个缺口，不重复首问。

## 动作追踪选择器

下表用于选择下一问，不是一次性问卷。每轮只能选一个问题。

| 信息缺口 | 推荐问法 |
|---|---|
| 事件来源 | 你怎么知道这件事发生了？ |
| 实际动作 | 你当时具体做了什么？ |
| 使用载体 | 这一步是在电脑、手机、微信、Excel、纸上，还是现场完成的？ |
| 软件位置 | 你当时打开的是哪个软件、哪个页面或哪张单子？名称记不清也没关系。 |
| 软件操作 | 在那个页面里，你是选了一项、填了内容、上传了东西，还是点了提交？ |
| 结果状态 | 提交以后，页面、单据、库存或订单显示了什么变化？ |
| 线下回录 | 这件事在线下确认后，谁会把结果录回哪个系统？ |
| 交接对象 | 做完以后交给谁，或者谁会收到消息？ |
| 完成信号 | 你怎么知道这一步已经处理成功？ |
| 异常处理 | 如果做不了或情况不一样，平时怎么处理？ |

## 模糊描述

用户说“在系统里处理一下”时，不问技术字段。可以问：

> 你当时在系统里大概做了什么？比如选了一项、填了内容，还是点一下确认？记不清名称也没关系。

如果仍记不清，保留已经确认的业务事实；把页面、按钮和字段写入待设计事项。“在系统中处理”不能直接作为终稿节点。

## 三层还原

对关键动作逐步补齐三层信息，但每轮仍然只问一个问题：

1. **业务动作**：岗位为了什么事情做了什么；
2. **软件操作**：在哪个系统或页面，选择、填写、上传或提交了什么；
3. **结果状态**：产生或更新了什么单据、库存、订单、审批状态或通知。

例如用户说“良品先入库”，应继续问实际怎样操作，直到能够确认类似“仓管在 ERP 采购收货单中录入良品实收数量并提交，系统生成入库记录并更新库存”。用户没有确认的系统名称、页面、按钮或状态不得自行补写。

执行者只记录岗位角色，如商务、销售、采购、仓管、财务、老板。多人参与时区分主责、协作和审批，不记录真实姓名。

## 阶段性复述

约 3–5 个动作后，用一句话复述：

> 我先确认一下：你收到订单后先看地址、商品和备注；正常就接单，缺货或送不到时先联系客户。这里有没有说错或漏掉？

复述不得加入用户未说过的动作。纠正完成后再继续。

## 异常补齐

主路径确认后，围绕已出现动作询问具体情况：

- 如果一直没人处理，平时会怎样？
- 如果对方不同意或一直不回复，平时怎么办？
- 如果只能完成一部分，是先做一部分还是等齐？
- 如果已经做完又要取消，谁来处理？
- 如果系统暂时用不了，你们怎么继续工作？

每次只问一个与当前流程最相关的问题。候选场景只有经用户确认存在，才能进入现状流程。

## 当前与未来

听到“应该、最好、希望、以后、准备”时，询问：

> 这是你们现在已经这样做，还是希望以后这样做？

当前做法进入现状流程；未来做法进入 `future_expectations`。

## 结束访谈

先展示纯文字草案，包括：主路径、异常路径、软件／线下交接、推导项、待设计事项、待确认问题。只有用户确认草案后才生成终稿文件。
