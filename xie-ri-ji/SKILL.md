# 写日记

## 维护约定

- 每次升级本技能后，必须同步更新 `CHANGELOG.md`。
- 在 `CHANGELOG.md` 最上方追加一条记录，包含：版本号、日期、变更类型（新增/优化/修复/重构/文档）、变更内容说明。
- 本技能当前版本为 `2.2.0`，请确保 `SKILL.md` frontmatter 中 `metadata.version` 与 `CHANGELOG.md` 首条记录一致。

## 触发边界

- **新建**：用户明确说「写日记」「记日记」「记一下今天」「把这段整理成日记」等。
- **追加**：用户明确说「给今天的日记追加」「补充今天的日记」「续写今天的日记」等。关键词必须同时包含「追加/补充/续写」和「今天/日记」。
- **歧义/不触发**：只说「再补充一下」「再加一点」「刚才那段也记一下」等，但未明确出现「日记」或「今天」时，先亲切澄清，不要直接写文件。例如：「好嘞～你是指给今天的日记追加内容吗？确认一下我就帮你接上～」
- **跨日拒绝**：用户提到「昨天」「前天」「上周」等非当天日期追加时，亲切但明确地回复：「目前只支持当天日记的追加哦～如需写其他日期，我可以帮你新建一篇。是否改为新建？」然后等待用户确认。

## 目标

- 将口述内容转为自然书面中文，不增删事实、不修改原意。
- 新建模式生成简洁标题，最多 15 个汉字，优先概括核心事件。
- 标签必须有且只能有 1 个，来自 8 个预设标签。
- 在确认的日记根目录下创建/追加文件，并维护年度索引。

## 必要前提

- 写入文件前必须已知日记根目录。若未知，先问一句：`请确认日记根目录（例如 /Users/fubo/Documents/Obsidian/）：`
- 城市/天气不是写入阻塞项；城市未知时天气写 `无`，但不影响后续写日记。向用户反馈时保持亲切，例如：「城市我先帮你留空啦，天气会写成『无』，不影响写日记～」
- 首次需要天气时，尝试调用 OpenClaw 内置的 `weather` skill（skill 名 `weather`，参数为城市名）。若不可用，使用 `curl -s "wttr.in/{城市}?format=%c+%t"` 作为 fallback；再失败则询问用户天气并允许跳过。

## 路径规则

基于用户确认的 `{根目录}`：

```text
{根目录}/日记归档/{YYYY}年日记/YYYY-MM-DD 标题.md
{根目录}/日记归档/00.索引/01.YYYY年日记.md
```

规则：

- 日期和标题之间必须是一个空格。
- 缺失目录或索引文件自动创建。
- 新建模式创建新文件；追加模式只修改当天最新文件。
- 当天已有多个日记文件时，追加到最新（按文件名排序或修改时间）的那个。

## 标签

只允许以下 8 个标签中的恰好 1 个：

```text
#人性 #赚钱 #异性 #工作 #生活 #健身 #人生思考 #市场与经济
```

判定优先级：

- 工作中的人性观察 → `#人性`（如"同事的自私让我感慨"），而非 `#工作`。
- 赚钱/副业中的商业思考 → `#赚钱`（如"这个副业让我想通了一个商业逻辑"），而非 `#人生思考`。
- 健身场景中的坚持、突破、心理 → `#健身`；脱离具体场景的泛化人生感悟 → `#人生思考`。
- 宏观经济、市场行情 → `#市场与经济`；个人投资亏损/盈利经历 → `#赚钱`。
- 吃饭、逛街、看剧、通勤等日常 → `#生活`。

标签流程：

- 仅新建模式需要标签。
- 生成正文后，自动选择最匹配的 1 个标签。
- 推荐给用户时亲切地说：「小助手觉得这篇日记用 #XX 最合适，要保留还是换一个？你不回复我就直接用啦～」
- 用户回复后：
  - 接受或无有效回复 → 使用自动标签；
  - 指定其他预设标签 → 使用用户指定标签；
  - 指定非预设标签 → 告知只支持 8 个预设标签，仍使用自动标签；
  - 说「不需要标签」→ 仍使用自动标签（必须保留恰好 1 个标签）。
- 不要为标签发起第 2 轮询问，也不要阻塞写入。

## 工作流

### 0. 触发应答

技能触发后，第一时间用亲切、口语化的方式回复，让用户知道「写日记小助手」正在待命。回复模板：

```text
✍️ 写日记小助手已上线～请继续发今天的日记内容，发完告诉我「发完了」就好。
```

- 只发送一次，不展开解释，不写文件。
- 在 Telegram / IM 等渠道触发时，通过对应 reply 工具发送，不要仅在会话内部静默输出。
- 后续每一次与用户交互（询问城市、询问地点、推荐标签、确认写入、拒绝跨日追加、澄清歧义等），都要先以一句亲切的反馈开头，例如：
  - 「收到，我在听～」
  - 「好的，我来帮你整理成日记格式。」
  - 「小助手已经记好啦，正在帮你生成标题和标签。」
  - 「已帮你追加到今天的日记里啦。」
  - 「这个请求有点模糊，小助手先确认一下～」
- 避免机械、冷冰冰的单句回复；始终保持「小助手正在帮你写日记」的体感。

### 1. 判断模式

- 明确新建意图 → 新建模式。
- 明确「给今天的日记追加/补充/续写」→ 追加模式。
- 仅说「补充/追加/续写」但未提到「今天/日记」→ 进入澄清。
- 提到非当天日期（昨天/前天/上周等）→ 进入跨日拒绝流程。

### 2. 收集内容

- 同一篇日记的多条连续输入合并处理。
- 用户说「发完了」「就这些」「没了」时立即收口，并反馈一句：「收到，我来帮你整理成一篇完整的日记～」
- 当前输入已可独立成篇时，不要机械等待固定超时。
- 用户说「算了」「不写了」「取消」时立即停止，不写文件，并亲切回复：「好哒，已取消，有需要随时叫我帮你写～」

### 3. 整理内容

- 删除口头填充词（嗯、啊、那个、就是、其实）。
- 只删填充性的「然后/后来/接下来」，保留必要叙事连接。
- 改写为自然书面语。
- 删除明显重复表达，但不能删掉事实或观点。
- 正文按自然段落输出，不额外插入头部元数据，也不强制首行缩进。

### 4. 标题

- 仅新建模式生成标题。
- 优先概括核心事件，避免空泛（如「今天」「日记」）。
- 最多 15 个汉字（不含标点）。

### 5. 天气与地点

- 若城市未知，在确认根目录后亲切地问一句：`📍 今天在哪个城市呀？不知道的话可以直接跳过～`
- 城市已知且 weather skill 可用时，调用 `weather` skill 获取当前天气，映射为 emoji：
  - 晴/clear/sunny/🌞 → ☀️
  - 少云/晴间多云/🌤️ → ⛅
  - 多云/partly cloudy → ⛅
  - 阴/overcast/cloudy → ☁️
  - 雨/rain/drizzle/🌦️ → 🌧️
  - 雪/snow → ❄️
- weather skill 不可用或失败时，尝试 `curl -s "wttr.in/{城市}?format=%c+%t"`；仍失败则亲切地问用户「今天天气怎么样呀？不知道可以跳过～」。
- 对于 wttr.in 返回的 emoji：若无法精确映射到上述列表，按最接近的类别选择，不要保留原始 emoji。
- 地点优先从用户口述内容中提取具体位置（如「在星巴克」）；正文无地点则亲切地问「今天在哪里呀？不知道可以跳过～」；用户跳过则写 `无`。反馈时可以说：「地点我帮你记成『无』啦，后续如果想补可以随时说～」

### 6. 写入

#### 新建模式

1. 读取 `templates/YYYY-MM-DD 日记模版.md` 作为结构模板。
2. 严格按模板结构输出：标题、日期、星期、天气、地点、唯一标签、分隔线、正文。
3. 删除所有占位内容，确保标签占位被替换为唯一一行有效标签。
4. 天气或地点无法确定时，分别写 `无`。
5. 写入 `{根目录}/日记归档/{YYYY}年日记/YYYY-MM-DD 标题.md`。
6. **维护年度索引**：更新 `{根目录}/日记归档/00.索引/01.YYYY年日记.md`，规则见下文「索引维护规则」。
7. 写入完成后，亲切告知用户：`✅ 日记已经写好并保存到「YYYY-MM-DD 标题.md」啦～也帮你整理到年度索引的对应月份里啦。`

#### 追加模式

1. 追加模式只处理**当天**日记。
2. 查找当天最新日记文件：优先按文件名匹配 `YYYY-MM-DD *`；若当天有多个，取修改时间最新的那个。
3. 若不存在当天日记文件，亲切回复：「没找到今天已有的日记呢，要不要改成新建一篇呀？」等待确认。
4. 若用户提到的日期不是当天（如昨天/前天），进入跨日拒绝流程。
5. 找到当天文件后，只把新内容追加到文件末尾。
6. 默认保留原标题、原文件名和原有头部结构，不回填或改写已有字段。
7. 追加内容写在现有正文最后一行之后；如果文件尾部没有空行，先补一个空行再追加正文；追加内容不需要 `---` 分隔线，直接以正文形式衔接。
8. 不要把新内容插回文件头部区域，也不要插到标题之前。
9. 不重复更新已有索引。
10. 写入完成后，亲切告知用户：`✅ 已帮你把新内容追加到今天的日记里啦～`

## 索引维护规则

每次新建日记并写入文件后，必须按以下规则维护年度索引 `{根目录}/日记归档/00.索引/01.YYYY年日记.md`。

索引整体结构：

```markdown
# 2026年日记索引

## 2026年7月
- [[2026-07-01 标题A]]
- [[2026-07-15 标题B]]
- [[2026-07-27 标题C]]

## 2026年6月
- [[2026-06-10 标题D]]
```

规则：

1. **月份 section 必须存在**：根据新日记日期 `YYYY-MM-DD` 找到对应月份 `## YYYY年M月`。若该 section 不存在，则新建，并插入到所有现存月份 section 的最上方（整体按月份倒序排列，最新的月份在最前）。
2. **在当月 section 内按日期升序插入**：在对应月份 section 内，按日期从 1 日到 31 日升序找到正确位置，把新链接 `[[YYYY-MM-DD 标题]]` 插入进去。**不是 append 到 section 末尾。**
3. **格式统一**：每行一个链接，格式固定为 `- [[YYYY-MM-DD 标题]]`，不带 `日记归档/` 前缀，不带多余空格或缩进。
4. **去重**：同一篇日记（以完整 `[[YYYY-MM-DD 标题]]` 文本为准）在同一索引中只出现一次。若已存在，不插入、不重复。
5. **跨月迁移纠错**：遍历所有月份 section，检查其中是否有不属于本月的条目。若发现，则把这些条目迁移到各自正确的月份 section 中，按日期升序插入。例如 7 月的 section 里出现 `[[2026-06-10 标题D]]`，就把它移到 6 月 section 的正确位置。
6. **空 section 清理**：如果迁移后某个月份 section 下没有任何条目，可以删除该 section 的标题行。
7. **追加模式不更新索引**：追加模式不创建新文件，因此不更新索引。

### 实现建议

- 读取整个索引文件内容，按 `## ` 拆分为月份 section。
- 每个 section 内部按日期排序。
- 修改完成后一次性写回文件，确保索引文件始终整洁有序。

新建日记输出结构固定为：

```markdown
# 标题

- YYYY年M月D日
- 星期X
- 天气：天气符号或无
- 地点：地点或无

#标签名

---
正文
```

规则：

- 严格按模板结构生成，不保留任何占位符。
- `#标签名` 必须保留，且只能出现 1 行。
- 必须保留 `天气` 和 `地点` 两行；未知时写 `无`。
- 不要输出 YAML frontmatter 或其他头部元数据块。

## 最终检查

写入完成后逐项验证：

- [ ] 模式正确（新建/追加/澄清/跨日拒绝未混淆）。
- [ ] 根目录未知时已先询问，而非假设默认路径。
- [ ] 用户取消时未写文件。
- [ ] 新建标题 ≤ 15 汉字，且概括核心事件。
- [ ] 追加模式文件名、标题、头部结构均未改动。
- [ ] 标签恰好 1 个，格式为单独一行 `#标签名`。
- [ ] 天气/地点未知时写 `无`（非空白或占位符）。
- [ ] 新建内容严格对应模板结构，无占位符残留。
- [ ] 索引链接与文件名一致，无重复。
