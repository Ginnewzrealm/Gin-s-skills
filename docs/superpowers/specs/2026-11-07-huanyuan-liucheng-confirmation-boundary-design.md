# 企业流程现状还原技能：确认门与流程边界设计

## 目的

更新 `huanyuan-liucheng`，让 Agent 在拿到访谈、会议纪要或文字资料后，先确认资料口径、流程边界和待确认问题，再生成正式 Markdown 与 HTML。案例资料只用于验证技能，不在本次改动中产出“网际”或“金华得创”的正式流程成果。

## 已确认的用户要求

1. 只还原公司当前实际运行状态，不把规范、建议、未来方案或数字化目标当成现状。
2. Agent 不能拿到资料就直接生成成果。必须先用文字提交理解、候选流程、拆分/合并判断和确认问题；用户明确确认后才能建模和渲染。
3. 输入可能同时包含多个流程。先判断流程数量，再决定哪些合并、哪些拆分；部门变化本身不是拆分理由。
4. 资料不完整、流程有空白或现状做法错误都允许存在。Agent 只还原，不补全、不优化、不美化。
5. 察觉缺环或衔接不明时，只转成具体确认问题；确认前不得把“可能存在的环节”画成节点。
6. 每个动作节点只包含一个主体和一个业务动作。
7. 每个决策支持 2–N 个分支，所有分支都必须显示条件和去向；需要时显示汇合节点。
8. HTML 上方流程图只显示路径、节点和分支。关键决策说明与待确认问题统一放在页面最下方，不能塞进流程图卡片。
9. 正确公司名称为“网际”。原始转录中的错误名称只保留在原始证据文件里，任何新模型、测试说明或成果均使用“网际”。

## 非目标

- 不在本技能中设计未来流程或提供优化建议。
- 不把“流程规范”自动认定为当前实际执行。
- 不为了图形闭合发明责任人、审批标准、阈值、动作或先后关系。
- 不在本轮交付网际或金华得创的正式业务流程文件。

## 方案选择

### 方案 A：只写提示语

在 `SKILL.md` 中提醒 Agent 先确认。改动最小，但无法阻止脚本在未确认模型上直接渲染，稳定性不足。

### 方案 B：确认门 + 模型约束 + 渲染约束（采用）

同时更新技能工作流、JSON 模型校验、HTML 渲染器和行为评测。确认行为由技能约束，正式渲染由模型中的确认状态机械拦截。这样既保留 AI 对边界的判断能力，又避免绕过确认直接出成果。

### 方案 C：建立完整的流程组合项目系统

新增多流程项目清单、数据库和可交互编辑器。超出当前需要，也会引入新的维护负担，暂不采用。

## 工作流设计

### 阶段 A：确认前分析

Agent 只在对话中输出以下内容，不创建正式文件：

1. 资料口径：哪些是现状、规范、目标、建议、项目计划或相互冲突的说法。
2. 候选流程清单：每个流程的核心业务对象、触发事件、结束状态和上下游关系。
3. 拆分/合并判断：给出判断理由，不能因用户要求“一张图”就跳过边界分析。
4. 确认问题：把资料缺失、跳步、冲突、责任不清和决策规则不全改写成业务人员可以直接回答的问题。
5. 明确停点：请求用户确认或纠正以上理解。

用户在看到这份确认前分析之后明确表示“确认”“按此执行”或给出修正，才算通过确认门。用户第一次上传资料时说“直接做”“不要问”“今天交付”，不等于已经确认 Agent 尚未展示的理解。

### 阶段 B：确认后建模与渲染

1. 按确认后的边界为每个独立流程建立单独模型。
2. 只写现状事实；目标和建议不进入现状模型。
3. 一个动作节点只写一个主体和一个动作。
4. 资料明确的错误做法照实连接；资料未说明的可能环节不进入图。
5. 未回答但用户允许保留的事项进入 `pending_questions`。只有当决策分支必须有目标且去向确实未知时，才允许使用中性的 `unresolved` 终点；不得把猜测动作写成节点。
6. 从同一模型生成 Markdown、HTML 和问题单。

## 流程边界规则

优先合并为同一流程：

- 围绕同一核心业务对象；
- 共享同一触发事件和业务结果；
- 位于同一连续生命周期；
- 后续步骤不能脱离前序步骤独立启动；
- 只是执行角色或部门发生变化。

优先拆分为独立流程：

- 核心业务对象发生变化；
- 出现独立触发事件和独立完成状态；
- 可以单独暂停、取消、重复或统计；
- 使用独立单据、台账或责任结果；
- 上游输出成为下游输入。

边界证据不足时先列为候选流程并提问，不强行合并或拆分。

## 模型变更

- `schema_version` 升级到 `2.0`。
- 新增顶层 `confirmation`：`status` 为 `pending` 或 `confirmed`，并记录用户确认的范围摘要。`render` 命令只接受 `confirmed`。
- `process` 新增 `business_object`、`trigger`、`end_state`、`boundary_reason`。
- `action.owner` 改为必填。
- `pending_questions` 从字符串改为对象：`id`、`text`、`related_nodes`。
- 新增可选 `join` 节点，用于显示多个分支汇合；它只表示路径汇合，不冒充业务动作。

## HTML 信息架构

固定顺序：

1. 标题、状态和统计；
2. 当前现状流程图；
3. 关键决策节点说明；
4. 待确认问题；
5. 资料来源与事实声明。

流程图节点只显示编号、主体、动作或决策问题。判断信息、判断标准、证据状态和完整分支说明只在下方“关键决策节点说明”中出现。待确认问题只在最下方单独列出，并标明关联节点。

流程图使用递归分支结构展示所有 2–N 分支，不再用“单一主线 + 右侧摘要”冒充完整路径。重复进入同一节点时显示汇合引用，避免复制整条后续路径。

## 基线失败与针对性约束

无新规则的 Agent 已出现：

- 把未来飞书方案放入现状成果底部；
- 因用户要求“不要拆”而把客户、采购、交付、回款和退货塞进同一流程；
- 在审批与出库之间自行加入“中间控制与交接机制未说明”节点。

新技能必须分别要求：目标内容直接排除；边界判断先于交付形式；缺失内容只生成确认问题，不能生成猜测节点。

## 验收标准

- 未确认模型无法渲染任何正式文件。
- 动作节点缺少主体时校验失败。
- 待确认问题具有唯一编号并引用有效节点。
- 流程图区域不出现判断信息、判断标准或问题清单正文。
- HTML 底部完整列出所有决策说明和待确认问题。
- 2–N 个分支条件都在流程图中可见。
- Markdown、HTML 和问题单来自同一 JSON，编号和内容一致。
- 行为评测中，Agent 会停在确认环节，并正确区分现状、目标和独立流程。
