# gin-business-process-mapper 设计规格

## 1. 目标

创建一个面向非技术业务人员的企业流程梳理 Skill。访谈对象只需使用日常语言描述实际工作、交接方式和异常处理；Skill 负责把这些叙述还原为可核对的业务流程，并翻译成软件开发可使用的操作、规则、状态和待设计事项。

Skill 固定交付两种用户成果：

1. Markdown 流程说明文档；
2. 单文件、可离线打开的 HTML 流程图与节点说明。

内部使用结构化 JSON 作为两种成果的唯一数据源，默认不把 JSON 作为用户交付物。

## 2. 用户与使用边界

### 2.1 主要用户

- 访谈者或实施顾问：通过自然语言与业务人员沟通；
- 非技术业务人员：只能描述日常动作、使用的工具、交接和异常情况；
- 产品、设计和开发团队：使用最终文档理解现状及软件实现含义。

### 2.2 适用场景

- 还原一家公司的采购、销售、订单、仓储、财务、售后等现行业务流程；
- 梳理现有软件中的操作流转，以及软件与微信、Excel、纸质单据、线下现场之间的交接；
- 为新软件或现有软件改造提供业务输入。

### 2.3 不适用场景

- 直接设计完整产品原型或数据库；
- 在没有业务证据时替用户补全“标准流程”；
- 把优化建议混入现状流程；
- 要求非技术访谈对象回答状态机、接口、数据模型等技术问题。

## 3. 核心原则

### 3.1 先还原事实，再翻译需求

Skill 必须把信息分为三层：

1. **现状事实**：业务人员明确描述或材料明确记录的实际动作；
2. **软件实现含义**：由现状事实提炼出的界面、能力、规则或状态需求；
3. **待设计事项**：现有信息不足，需由产品或开发团队决定的内容。

推导内容不得写成用户已确认的事实。每条关键结论应能追溯到对话、文件或用户确认。

### 3.2 使用业务语言访谈

对业务人员提问时避免“节点、状态机、触发器、数据源、校验规则、异常分支”等术语。优先使用：

- “后来发生了什么？”
- “你怎么知道轮到你处理了？”
- “你当时具体做了什么？”
- “是在电脑、手机、微信、Excel、纸上，还是现场完成的？”
- “做完以后，谁会知道？”
- “如果做不了，平时怎么处理？”

一次只问一个最自然的后续问题。已有答案不重复询问；用户说不知道或记不清时，记录为待确认。

### 3.3 真实案例优先

每条流程优先从最近一次真实业务开始，而不是要求用户抽象概括标准流程。完成实例还原后，再询问常见变化和例外，以减少记忆偏差和理想化描述。

### 3.4 区分当前做法与未来期望

当用户说“应该、最好、以后想要”时，Skill 必须确认这是当前做法还是期望做法。未来期望放入独立章节，不得进入现状主流程。

## 4. 对话协议

### 4.1 启动与边界

先确认本次梳理的流程名称、业务起点和大致终点。若用户无法命名流程，可使用临时名称，完成主路径后再确认。

推荐首问：

> 我们先不讲标准流程。就拿最近一次真实发生的业务来说，你最开始是怎么知道这件事需要你处理的？

### 4.2 动作追踪循环

围绕用户刚刚描述的内容，自适应选择下一个问题：

| 信息缺口 | 业务语言问题 |
|---|---|
| 事件来源 | 你怎么知道这件事发生了？ |
| 实际动作 | 你当时具体做了什么？ |
| 使用载体 | 这一步是在什么地方完成的？ |
| 交接对象 | 做完以后交给谁，或者谁会收到消息？ |
| 完成信号 | 你怎么知道这一步已经处理成功？ |
| 异常处理 | 如果做不了或情况不一样，通常怎么办？ |

这张表是提问选择器，不是一次性问卷。每轮只问一个问题。

### 4.3 模糊描述的处理

当用户说“在系统里处理一下”等模糊表述时，使用识别式追问：

> 你当时在系统里大概做了什么？比如选了一项、填了内容，还是点一下确认？记不清名称也没关系。

不得要求用户回忆准确按钮文案。用户无法确认时，保留业务动作，并把界面细节记录为待设计事项。

当用户能够描述软件操作时，继续用生活化问题还原三个层次：

1. **业务动作**：谁为了什么事情做了什么；
2. **软件操作**：打开哪个系统或页面，选择什么选项、填写什么内容、执行什么操作；
3. **结果状态**：提交后生成或更新了什么单据、库存、订单、审批状态或通知。

不得把“良品先入库”“系统里处理一下”等概括直接作为终稿节点。应继续询问实际录入方式、提交动作和提交后的可观察结果。若某一步在线下完成，必须记录电话、微信、纸单、现场或实物交接等载体，以及谁把线下结果录回哪个系统。

### 4.4 阶段性复述

每取得约 3–5 个连续动作，使用日常语言简短复述：

> 我先确认一下：你收到新订单后，先看地址、商品和备注；正常就接单，缺货或送不到时先联系客户。这里有没有说错或漏掉？

用户纠正后再继续。复述用于验证事实，不加入新的行业常识。

### 4.5 异常场景补齐

主路径确认后，围绕已经出现的动作提出具体场景，例如超时、拒绝、取消、重复、部分完成、找不到人、系统不可用。不得直接要求用户“穷举所有异常分支”。

只有用户确认真实存在的异常才进入现状流程；合理但未确认的候选进入待确认清单。

### 4.6 草案确认

完成一条流程后，先展示文字化主路径、异常路径和待确认项。用户确认后才生成最终 Markdown 和 HTML。若用户只要求阶段性草稿，文件必须显式标注“草稿”。

## 5. 结构化流程模型

### 5.1 流程级字段

```text
process_id
process_name
purpose
scope_start
scope_end
participants[]
systems_and_channels[]
nodes[]
edges[]
scenes[]
open_questions[]
future_expectations[]
sources[]
version
status: draft | confirmed
```

### 5.2 节点字段

```text
id
name
kind: start | action | decision | end
business_fact
actor_role
execution_mode: manual | automatic | assisted
carrier: system | chat | email | spreadsheet | paper | onsite | other
carrier_name
entry_or_signal
business_action
software_location
software_operation
interface_implications[]
inputs[]
outputs[]
completion_signal
state_before
state_after
rules[]
exceptions[]
evidence_status: confirmed | inferred | unknown
evidence_refs[]
```

`business_fact` 只写现状事实；`interface_implications` 和推导出的状态、规则必须保留 `inferred` 标记，直到用户或产品人员确认。

`actor_role` 只记录岗位角色，如商务、销售、采购、仓管、财务、老板，不记录真实姓名。多人参与时分别用主责、协作、审批角色表达。

决策节点额外包含：

```text
decider_role
criteria[]
fallback
```

`software_location` 记录系统和页面位置，`software_operation` 记录选择、填写、提交等界面动作。无法从访谈确认时保留为空并进入待确认项，不得根据常见软件习惯补写。

### 5.3 连线字段

```text
id
from
to
label
condition
kind: normal | decision | exception | timeout | cancel | rework
evidence_status
evidence_refs[]
```

### 5.4 场景字段

```text
id
name
type: main | exception | variant
owner_roles[]
edge_ids[]
boundary_rule
```

每个流程至少包含一个主场景。异常、退回、取消和返工使用独立场景表达，但仍引用同一组节点和连线。`boundary_rule` 说明场景从何种真实情况开始、在何种结果下结束或返回其他场景。

## 6. 输出设计

### 6.1 Markdown 文档

文件名：`<流程名称>-流程说明.md`

正文以业务人员易读的“场景卡片”为中心，而不是逐节点技术清单。固定顺序：

1. 流程概况与范围；
2. 参与角色与使用载体；
3. 场景流程，先主场景，再异常场景和变体场景；
4. 软件操作与状态变化；
5. 产品待设计及待确认事项；
6. 事实来源与确认状态；
7. 节点明细附录。

每张场景卡片包含场景名称、树状流程、主责/协作/审批角色、进入该场景的分界线以及关键判断依据。树状流程放入等宽代码块，使用 `│`、`├─`、`└─`、`▼` 和 `◇` 表达顺序、分支和决策。生成器按 Unicode 显示宽度计算缩进，确保中文、英文、数字和线框符号对齐；分支组之间保留空行，长文本使用续行缩进，避免横向过宽和纵向拥挤。

流程动作必须尽可能写清软件落点。例如“仓管在 ERP 打开采购收货单 → 录入良品实收数量 → 提交收货 → 系统生成入库记录并更新库存”。线下步骤应直接标出载体及回录点，例如“采购通过电话与供应商确认 → 在 ERP 创建采购退货单”。

节点继续使用统一编号 `N01`、`N02`……，与 HTML 完全一致，但编号和技术字段主要出现在附录，不干扰正文阅读。

### 6.2 HTML 流程图

文件名：`<流程名称>-流程图.html`

HTML 为单文件、无网络依赖，包含：

- 白底、青绿色标题、横向主流程；
- 开始/结束为圆角节点、日常动作为矩形、决策点为菱形；
- 正常主线、上下分支、异常回流，回流线从主流程下方返回；
- 连线直接标注判断条件；
- 多场景使用场景切换展示，打印时按场景依次展开；
- 点击节点定位至下方节点说明；
- 节点说明展示岗位角色、现状事实、线上或线下载体、软件位置、界面操作、状态变化、规则和证据状态；
- 待设计事项与待确认项使用不同视觉标识；
- 支持窄屏横向滚动、键盘访问和浏览器打印。

当节点过多导致单图难以阅读时，HTML 显示一张业务总览图，并按阶段生成局部详图。不得通过无限缩小文字强塞进一张图。

### 6.3 一致性要求

Markdown 和 HTML 必须由同一份 JSON 生成。验证器至少检查：

- 节点 ID 唯一且连续；
- 连线 ID 唯一；
- 每条连线引用存在的节点；
- 每个决策节点至少有两条带有不同条件的出边，并具备决策角色、判断依据和无法判断时的处理方式；
- 返工或取消连线可以构成回路，普通主线不得构成无限推进的回路；
- 每个场景引用存在的连线；终稿中所有连线都必须归属场景；
- 开始和结束范围明确；
- 两种输出包含相同节点、连线、规则和证据状态；
- 推导项未伪装为确认事实；
- HTML 不包含外部 HTTP/HTTPS 依赖。

验证器同时给出表达质量警告：业务动作、判断依据和场景边界若只写“处理、跟进、弄一下、看情况”等模糊词，应提示继续访谈。该检查只提供警告，不自动改写业务事实。

## 7. Skill 目录与职责

```text
gin-business-process-mapper/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── interview-protocol.md
│   ├── process-schema.md
│   └── output-rules.md
├── assets/
│   └── process-report-template.html
├── scripts/
│   ├── render_process.py
│   └── validate_process.py
├── tests/
│   ├── fixtures/
│   ├── test_renderer.py
│   └── test_validator.py
└── evals/
    └── evals.json
```

- `SKILL.md`：触发条件、核心原则、工作流和引用路由；
- `interview-protocol.md`：非技术访谈语言与自适应追问规则；
- `process-schema.md`：结构化数据字段、枚举和证据状态；
- `output-rules.md`：Markdown、HTML 和一致性要求；
- `process-report-template.html`：已确认原型的视觉基础；
- `render_process.py`：从 JSON 确定性生成 Markdown 与 HTML；
- `validate_process.py`：在生成前验证结构和事实标记；
- 测试：覆盖结构验证、双格式一致性、HTML 离线性和关键转义；
- evals：覆盖非技术叙述、异常流程、当前与未来混杂、信息不足四类真实请求。

## 8. 错误处理

- 输入缺少关键边界：继续梳理已知部分，并把受影响问题加入待确认清单；
- 用户回答矛盾：引用两种说法，用日常语言请求确认，不自行选择；
- 节点无法连接：保留为“未确定交接”，不强行补边；
- HTML 布局过密：自动切换为总览图加分阶段详图；
- JSON 验证失败：不生成“终稿”，输出具体错误位置；
- 输出文件已存在：使用版本号或明确的更新操作，避免静默覆盖。

## 9. 验证策略

### 9.1 技能行为基线

在编写 Skill 前使用真实场景验证无 Skill 时的典型失败：

- 向非技术用户连续询问字段、按钮、状态等技术问题；
- 把推测的页面设计写成现状事实；
- 只生成业务概览，缺少软件实现含义；
- Markdown 与 HTML 的节点或分支不一致。

### 9.2 脚本测试

采用 TDD：

- 先编写验证器和渲染器的失败测试；
- 确认测试因功能缺失而失败；
- 实现最小代码；
- 运行本技能测试和仓库全量测试。

### 9.3 验收标准

一个非技术业务人员可以只描述日常动作完成访谈；最终成果应让产品或开发人员看清：

- 当前业务实际怎样流转；
- 软件、人工和线下动作在哪里交接；
- 哪些决策改变后续路径；
- 哪些软件需求来自已确认事实；
- 哪些内容仍需产品设计或业务确认；
- Markdown 和 HTML 是否表达同一条流程。

## 10. 第一版范围

第一版支持单公司、多条独立流程，但每次专注梳理一条流程。暂不实现拖拽编辑器、数据库、多人协作、在线发布、BPMN 导入导出或全公司自动拼接巨型总图。后续只有在真实使用证明必要时再扩展。
