# 确认前分析与纯文字提取方法

## 先判资料性质

逐条标记材料中的陈述：

| 类别 | 识别信号 | 处理 |
|---|---|---|
| 当前实际 | 现在、目前、实际、平时、经常、谁正在做 | 可进入现状候选 |
| 规范要求 | 应当、必须、禁止、制度规定、流程规范 | 不自动等于现状，先确认是否执行 |
| 目标方案 | 希望、未来、计划、上线后、要实现、自动化 | 直接排除当前态 |
| 项目计划 | 两天内、下一步、培训、迁移、待办 | 直接排除当前态 |
| 冲突/未知 | 两份材料说法不同，或无法判断时态 | 保留证据并提问 |

用户明确纠正公司名、角色名或事实时，以用户修正为准；原始文件保留原文并记录修正依据。例如原始转录写错公司名时，不改写证据文件，但新模型统一使用用户确认的名称。

## 建立候选流程清单

对每组动作先写四项：

1. 核心业务对象：谁的什么状态在变化，例如销售订单、采购订单、应收款或退货单。
2. 触发事件：什么发生后流程开始。
3. 结束状态：达到什么业务状态后本流程结束。
4. 上下游接口：本流程接收什么输入，输出又交给哪个流程。

### 合并信号

- 同一核心业务对象；
- 同一触发到同一结果；
- 位于同一连续生命周期；
- 后续动作无法脱离前序步骤独立启动；
- 仅仅角色或部门改变。

### 拆分信号

- 核心业务对象变化；
- 有独立触发事件和独立完成状态；
- 可以单独暂停、取消、重复或统计；
- 使用独立单据、台账或责任结果；
- 上游输出成为下游输入。

拆分信号相互矛盾或证据不足时，列为两个候选流程并提问，不为了得到一张完整图强行选择。

## 提取单个流程

1. 列角色：谁发起、谁执行、谁判断、谁审批、谁关闭。
2. 拆动作：每个动作写成“一个角色 + 一个动词 + 一个对象”。“业务员填写订单并关联客户档案”拆成两个动作。
3. 排顺序：只有原文明确或用户确认的关系才建立连接。段落相邻、版面相邻不等于流程相邻。
4. 找决策：凡是不同条件导致不同后续动作，都建立 `Dxx`。
5. 拆决策：分别写判断信息、判断标准、2–N 个分支条件和去向。
6. 找汇合：多个分支进入同一后续节点时使用 `Jxx`，不重复整段后续路径。
7. 查缺口：检查触发、否决、异常、退回、超时、重复提交、交接和结束状态。
8. 生问题：把每个缺口改写成业务人员可以直接回答的问题。

## 缺失与错误现状

- 资料没有说明某一步，不等于企业实际没有这一步。先问，不画。
- 用户确认当前确实直接跳过某一步，就按直接连接还原，不优化。
- 不创建“可能存在库存检查”“中间控制未说明”等猜测动作节点。
- 决策分支必须有目标、但去向确实未知且用户允许保留草案时，可以使用 `Uxx`，标签只写“后续去向未确认”，具体问题放在问题清单。
- 输入只给成功主线时，不替企业发明失败处理。

## 确认问题优先级

1. 这段描述的是当前实际做法，还是规范/目标？
2. 哪些动作属于同一个流程，哪些是独立上下游流程？
3. 谁拥有最终判断权？
4. 触发或不触发的精确条件是什么？
5. 多个条件是“任一满足”还是“同时满足”？
6. 拒绝、异常或不符合后去哪里？
7. 相邻节点之间是否还有实际动作或交接？
8. 什么状态才算流程结束？

## 确认前回复模板

在对话中一次性提交：

1. **资料口径**：哪些采用为现状，哪些排除，哪些需要确认。
2. **候选流程**：名称、业务对象、触发、终点、拆分/合并理由。
3. **待确认问题**：只问会改变边界、节点或分支的问题。
4. **停点**：请用户明确确认或修正后再生成成果。

不要创建确认单文件；确认环节发生在文字对话中。
