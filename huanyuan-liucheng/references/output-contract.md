# 输出契约

## 生成前提

正式输出只能在用户看过确认前分析并明确确认后生成。`confirmation.status` 不是 `confirmed` 时，渲染器必须拒绝并且不创建文件。

## 唯一事实源

每个独立流程一份 `model.json`。Markdown、HTML 和问题单都由 `scripts/process_model.py` 生成。需要修改时先更新 JSON，再重新生成，禁止分别手写。

## Markdown 流程说明

必须包含：

1. 公司、流程名称、边界、状态、决策数和待确认数。
2. 从起点到全部终态/未知去向的文字决策树。
3. 每个 `Dxx` 的决策人、判断信息、判断标准、证据状态、全部分支条件和去向。
4. 带 `Qxx` 和关联节点的完整问题清单。
5. 资料来源和“不补造、不优化”的事实声明。

## HTML 决策路径图

页面顺序固定为：

1. 标题、流程状态和统计；
2. 当前现状流程图；
3. 关键决策节点说明；
4. 待确认问题；
5. 资料来源与事实声明。

### 当前现状流程图

- 只显示节点编号、主体、动作/决策问题、分支条件、去向和路径汇合。
- 不显示判断信息列表、判断标准证据或完整问题正文。
- 所有 2–N 个分支必须作为可连续阅读的路径出现，不能只保留一条主线。
- 多个分支进入同一节点时显示 `Jxx` 或汇合引用。
- 蓝色动作、黄色决策、紫色汇合、红色未知去向、绿色终态。

### 页面底部

- “关键决策节点说明”完整列出决策人、判断信息、判断标准、证据状态、分支条件和去向。
- “待确认问题”只列问题，显示 `Qxx` 和关联节点；不得混入优化建议。
- 长文字自动换行，窄屏改为单列，打印时不依赖背景图或外部资源。

HTML 必须是单文件、离线可打开，不加载外部脚本、字体或样式。

## 待确认问题单

按对流程边界和决策路径的影响排序。问题要具体到资料性质、触发事件、责任人、条件组合、分支去向、交接关系或结束状态，避免“请补充更多信息”。

## 一致性检查

- Markdown 和 HTML 的 `Dxx` 集合相同。
- 同一分支的 `condition` 和 `target` 相同。
- 三份输出的 `Qxx`、问题正文和关联节点相同。
- HTML 流程图区域没有决策证据和问题正文。
- 输出状态为“已确认”时，严格校验通过。
