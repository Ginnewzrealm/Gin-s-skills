# 输出与验收契约

## 一次、一个流程、一份 Markdown

用户已看过现状、排除目标、单个流程的边界、关键决策和未知项，并明确允许生成。记录真实确认，不把同意排版当作业务规则已确认。

唯一交付物是 `NN 流程名-流程说明.md`，固定三个主体部分：

1. **流程图**：一个 `text` 代码块中的连续完整流程树。
2. **关键决策节点**：判断人、判断信息、已知标准、全部已知分支条件与去向、未知项。
3. **待确认问题**：具体、可回答，关联相应节点；未能确定接入点的已知动作也在此说明。

公司、状态与业务边界放顶部，资料来源放底部。不另交 HTML、问题单、阶段图、第二种排版或其他流程文档。模型留作内部工作文件。

## 连续展示与间距

- 从一个实际起点连续展开全部已知路径；阅读主线不需要跳到另一阶段、标题或代码块。
- 不按收件、收费、检测、维修、送厂等阶段分树。这些是否属于一个流程，先用业务边界判断，不能用排版代替判断。
- 顺序动作同列紧排，用 `↓` 表达先后；缩进只表达分支从属，避免每经过一个动作都向右缩进。
- `◆ Dxx` 标记真正改变去向的决策；`├─【条件】`、`└─【条件】` 接对应动作。条件、动作、去向紧排。
- 新决策前后、复杂兄弟分支之间用一行 `│` 分组；简单叶子分支连续排列。不用阶段标题或空白代码块切断主线。
- 首次遇到下游节点就展开；公共后续仅展开一次，其他实际汇合用 `↪ 汇入 ID`，实际回路用 `↩ 返回 ID`。引用只能指向树内已经展开的节点。
- 完整保留条件中的阈值、适用范围、任一／同时关系。不能为缩短文字省掉条件，也不能从一条结果推造另一条。
- 部分决策只展示原文已给出的结果，未说明的分支列在文末；未知去向使用 `… Uxx`，不能伪造成“完成”。
- 不能确定先后的已知动作写入对应问题的 `known_facts`，保留证据；不另画小树，不接入没有依据的箭头。

## 验收

- **边界**：一个业务对象／结果的生命周期；多个独立业务不能靠总标题、共同起点或无依据箭头合并。
- **证据**：动作、判断、条件、每条连接分别核对原文；未知不能靠脚本通过而升级成事实。
- **覆盖**：所有模型节点和有向边均在树中呈现，决策全部已知出口可追踪；真实汇合不重复整套后续。
- **交付数量**：生成命令只返回一个 `.md`，问题在该文档内部；本次只选一个流程。
- **实际阅读**：打开生成的 Markdown，沿主线和异常分支读到真实终态或断点，检查等宽缩进、紧排与分组留白。

脚本限制格式和结构，业务判断仍需原文核对与用户确认。不能把测试通过声称为任意自然语言输入都能百分之百正确。
