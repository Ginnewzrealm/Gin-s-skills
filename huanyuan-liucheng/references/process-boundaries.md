# 一个完整业务流程的边界

完整流程围绕一个业务对象或同一业务结果，从实际触发沿生命周期走到业务终态或资料明确的边界，包含正常、异常、退回和处理变体。资料没讲清结尾时保留断点，不为了“完整”补造动作。

## 六道判断，按顺序问

1. **是不是同一业务对象？** 同一对象的连续生命周期倾向合并；对象与处理结果都独立时倾向拆分。不能只按单据名称机械判断。
2. **B 能否不依赖 A 独立启动？** 能独立启动，可能是两个流程；必须承接 A 的产出，倾向同一流程中的环节或子流程。上下游依赖本身不能单独决定合并。
3. **有没有独立终态？** 可独立完成、拒绝、失效并结束业务责任，是拆分依据；同一流程的成功、失败结果不自动成为两个流程。
4. **有没有独立单据、台账或统计？** 独立业务管理加强拆分理由；只有一张单据上的审批意见通常是内部环节。
5. **是不是原流程的异常分支、子流程或变体？** 逾期催收可作为回款的异常子流程；零散发货、上门安装若服务同一交付结果，通常是交付变体。不因分支复杂就另立流程。
6. **是否仅仅换部门、角色、系统或阶段？** 这些说明交接，不能作为拆分依据。

综合判断后向用户说明本次边界。报价与合同订单可因同一商业机会合并，也可因独立报价台账与失效管理拆分；交付与收货验收要看验收是否独立管理，不能套用固定拆法。品牌结案与返利若只是结案中的品牌分支，保留为子流程。

## 输出边界与资料缺口

- 一次选一个一级流程，在同一树中还原其范围内相关子流程、异常和变体，不再按阶段分图。
- 识别出多个独立流程时，在对话里确认当前选择；本轮只交付所选流程的一份 Markdown。
- 实际汇合与回路可引用已展开节点；首次出现的后续直接展开，不跳到后面的阶段树。
- 已知动作存在但无法定位先后时，把已知动作与证据、接入点问题写在文末对应问题中，不另起碎片图，也不伪造连接。
- 完整性检查揭示缺口；不能用无证据箭头把不同业务拼成表面完整的一条链。
