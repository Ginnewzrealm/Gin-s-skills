# 企业流程现状与决策还原

> Copyright (c) 2026 Gin. All rights reserved. Proprietary material; no permission to copy, modify, distribute, commercialize, or create derivative works without prior written permission. See [LICENSE](LICENSE).

输入是自然语言文字，成果是公司当前实际运行的流程。**一次只交付一个 Markdown 文档，一份文档只还原一个完整业务流程。**固定包含：**流程图 → 关键决策节点 → 待确认问题**。流程图是在一个 `text` 代码块中连续展开的完整流程树。

完整流程按业务对象、触发、生命周期和结果边界判断。同一返修件的收件、收费、维修、转厂、寄回属于流程内的环节与分支，不能拆成多棵树再用“转至”拼接。完整性指覆盖已知路径；现状缺失、错误或没有规则时如实保留，不替企业补全。

## 输出前先对话确认

**拿到新资料，先理解并与用户沟通；用户明确允许按所展示的理解生成后，才能建立正式流程模型和输出文件。** 用户不需要填写表格、使用术语或回复固定口令。

确认前必须在自然语言对话中讲清以下内容，可以用短段落或简短列表：

1. **我理解的现状事实**：现在谁在做什么、实际如何交接；区分原文直接说明和仍待核实的理解。
2. **我识别的预期目标**：哪些是希望、计划、未来方案；明确这些不进入现状流程。制度要求单独说明，尚未确认执行时不算现状。
3. **准备还原的流程与边界**：资料中有几个候选流程，本次只还原哪一个、从哪里开始、讲到哪里；用业务对象和生命周期说明关键拆分或合并理由。其他独立流程只在对话中列为候选，本次不输出。
4. **关键决策节点**：逐个用业务语言描述“谁判断什么；已知有哪些条件；不同结果分别去哪里；哪些尚不清楚”。确实没有证据支持的决策时，明确说尚未识别到，不凑决策。
5. **需要确认的理解和缺口**：优先问会改变节点、分支或边界的问题，并说明哪些未知项可在用户允许后保留到成果底部。

最后自然地邀请用户确认或纠正，例如：“我理解现在按金额分给主管或老板审核；全员签章后发货是后续目标，本次不画进去。这样理解对吗？未说明的急单处理，我先列为待确认，可以吗？”然后停下等待。

- 首次说“直接做”“今天交付”，不是对尚未展示的理解作出的确认。
- “理解对，先按这个出，其他暂时不知道”等自然回复可授权生成含待确认项的草案。
- 用户只纠正一个人名或条件，不等于确认其余全部内容。吸收纠正，用简短话确认影响到的理解。
- 已确认的内容不重复询问。新资料改变流程边界、事实口径或关键路径时，只确认变更部分。
- 用户仅要求美化已指定且认可的文档时，保留其业务内容、节点、条件和连接；不借排版重新分析业务。视觉验收不等于补齐其中的未知规则。

具体识别方法与对话示例见 [references/interview-protocol.md](references/interview-protocol.md)。

## 建模时的判断规则

- **现状与目标分开**：根据整段语境识别，不能只凭“必须”“希望”等词机械分类。未证实执行的制度、目标、建议和项目计划不进入当前路径。
- **先定流程边界**：读取 [references/process-boundaries.md](references/process-boundaries.md)，按六道判断区分一级流程、子流程、异常分支和变体。跨部门不自动拆分，连续文字不自动合并；一个总标题或一个起点也不能证明多个业务属于一个流程。
- **动作具体**：新建动作节点为一个主体执行一个动作，写清对象。原文没有说明“合同要素”是什么，就保留问题，不替它补成价格、签章等检查。
- **决策改变路径**：判断或审批的不同结果会导致不同后续走向，才建 `Dxx`。核对、填写、签署等动作本身不是决策。
- **分支有条件和去向**：完整判断支持 2–N 个结果、汇合及真实退回重审。资料只讲出部分结果时，仅保留已知分支，标记分支集合不完整并提问，不凑第二条分支。多个风险可能同时成立时先确认处理关系，不能强行改成互斥四选一。
- **未知不能补造**：标准、条件组合、动作顺序或去向未知就提问。不能从“紧急项目须特批”推出“未签章 → 特批”，不能从两个相邻段落推出连接。
- **不强迫闭环**：资料未讲到结束，不新增“完成”；真实流程有错也照实还原。未知去向用中性断点表示，具体疑问放在底部。

## 确认后建立唯一事实源

本次选定的流程使用一份内部 `model.json`，Markdown 从它生成。模型记录原文片段、来源、事实类别和用户实际确认回复；动作、决策、分支和连线分别引用依据。读取 [references/process-model.md](references/process-model.md) 建模；`tests/fixtures/sales-order.json` 仅作结构示例。模型保留在工作目录，不追加成用户交付物。

确认记录只记录本次实际发生的对话，不复制示例中的“用户已确认”，不由 Agent 自己编写用户同意。未知规则的保留许可与业务规则已确认是两件事。

对照证据逐项复核：引用存在不等于支持结论。脚本可以发现缺引用、引用不存在和误用目标等问题，不能代替 Agent 判断原文是否支持这个动作、阈值或连接。

## 校验与生成

当前生成命令只需要 Python 3，不调用 HTML 布局器。

```bash
python3 <skill-dir>/scripts/process_model.py validate <model.json>
python3 <skill-dir>/scripts/process_model.py render <model.json> --output-dir <output-directory>
```

未取得可核对的确认记录时，生成命令拒绝且不得创建成果。全部业务规则已明确时可加 `validate --require-confirmed`；存在未知项的合法草案不需要通过此严格模式。

唯一交付文件：`NN 流程名-流程说明.md`。关键决策和问题都放在同一文档下方，不另外生成 HTML、问题单、第二种排版或其他流程的文档。

生成前读取 [references/output-contract.md](references/output-contract.md)，格式示例见 [sample-output/03 销售订单-流程说明.md](sample-output/03%20销售订单-流程说明.md)。使用同一生成器，不为案例另写按阶段截断路径的呈现逻辑。示例公司、角色、条件不得带入新资料。

## 交付前验收

1. **对话**：用户确实看过现状、目标、流程边界和关键决策的理解，并允许生成；未擅自把纠正当作全量确认。
2. **内容**：所有业务动作、条件与连接有相应依据；现状不混入目标；每个未解决缺口有可回答的问题；没有为排版补节点。
3. **范围与数量**：只有一个已确认的业务流程、一个 Markdown 交付物、一个主流程 `text` 代码块。无阶段子图、分支子文档或额外问题单。
4. **路径与排版**：从起点沿每条已知分支，在同一棵树中读到真实终态、实际返回或中性断点；公共节点仅展开一次，只有真实汇合或回路可引用已展开节点。连续动作紧排、决策分组留白；未知顺序不能借排版补造。
5. **状态**：技术校验通过不等于业务事实全部确认。不合格先修复并复查；不能以“脚本运行成功”宣称视觉或业务正确。
